## Why

Every view built after this is built against whatever data the developer has. Two
rows of `foo` hide the things this app is about: a company that bills for another
company's work, a person with two affiliations, a retainer running over its hours
allowance, an engagement with no end date.

The mockup already contains a considered dataset that exercises all of it —
EZDeploy billing for W+K, Sand & Sage's equity position, an overrunning retainer,
a proposed SOW. Porting it is cheaper than inventing it twice, and it makes every
later view reviewable against the mockup screen for screen.

## Scope

**In:**

- Extract the mockup's seed arrays — 10 companies, 7 people, 11 engagements, 11
  todos, 10 activity rows, 5 categories, 9 services with their versions, and the
  links attached to each company — into a fixture the seed script reads.
- Map the mockup's shorthand onto the real schema: `bills` → `bills_directly`,
  `via` → `billed_via_company_id`, `co` on a person → an `affiliations` row,
  `lastTouch` → `last_touch_at`, `model`/`status` to their lowercase enum values.
- Derive `activity` rows so `last_touch_at` is *consistent with* the activity log
  rather than set independently — the mockup stores both and they must not
  disagree once P1-05 maintains the column.
- `npm run seed`, guarded: it refuses to run against a non-empty database unless
  explicitly forced, so it can never silently destroy real data.

**Out:** `revenue_lines`, `milestones` and `time_entries` rows — those tables
arrive in Phase 3 and 4, and seeding them now would encode a guess about a
generator that does not exist. Note in the outcome that the fixture will need
extending when P3-05 lands. FTS5 population, which P1-06's triggers handle.

## Touches

- `electron/main/db/seed/fixture.ts` — the extracted data
- `electron/main/db/seed/index.ts` — the loader
- `package.json` — the `seed` script
- A test asserting row counts

## Acceptance

- [ ] `npm run seed` populates a fresh database and exits 0
- [ ] Row counts match the mockup exactly: 10 companies, 7 people, 11
      engagements, 11 todos, 10 activity rows, 5 categories, 9 services
- [ ] W+K and Programetrix have `bills_directly = false` and
      `billed_via_company_id` pointing at EZDeploy
- [ ] The Samay engagement has `billing_company_id` = EZDeploy and
      `client_company_id` = W+K — the case the whole model exists for
- [ ] Sand & Sage's equity engagement has `billing_model = 'equity'` and no rate
- [ ] Two services carry two `service_versions` each, with non-overlapping
      effective ranges
- [ ] Every company's `last_touch_at` equals the most recent `activity.occurred_at`
      for that company
- [ ] Running `seed` against a populated database refuses without `--force`

## Risks

- **The mockup's dates are relative to 27 August 2026.** Seeded verbatim, the
  cadence and overdue states drift as real time passes and Today's "going quiet"
  list changes meaning month by month. Decide whether dates are absolute (honest,
  ages over time) or offset from today at seed time (always demonstrates the
  states, but is not reproducible). Say which in the outcome — P2-03's decay work
  and X-07's performance harness both depend on knowing.
- The mockup uses `Title Case` for status and kind (`Active`, `End client`) where
  the schema uses lowercase enums. A silent mismatch produces rows that store
  fine and match no query.
- `last_touch_at` set independently of activity is the inconsistency P1-05
  exists to prevent. Deriving it here means the seed cannot teach a habit the
  repository forbids.
- A seed that truncates tables to be idempotent is a data-loss tool one flag away
  from a real database. The guard is not optional.
