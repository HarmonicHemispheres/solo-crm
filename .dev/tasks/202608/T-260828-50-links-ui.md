## Why

The last piece of §6.10, and the half that decides whether the feature is used.
A links section that needs a dialog, a kind dropdown and a title field before it
will accept a URL is one nobody fills in, and then the CRM stops being the place
that remembers where the contract lives. Pasting is the whole interaction: the
host decides the kind (T-260828-48) and the title defaults from the URL, so the
common case is one gesture.

The mockup already draws these rows; this task ports them.

## Scope

**In:**

- The links section on company detail, showing each link's favicon, kind icon,
  title and host, taken from the mockup rather than invented.
- **Paste to add** — pasting a URL into the section adds a row with the right
  icon and no dialog. Typing a URL and pressing Enter does the same.
- Inline title editing, saving on blur or Enter and reverting on Escape.
- Removing a link, with the same refusal handling as every other mutation —
  `RefusalError.blocker` carried as structured data, not a parsed sentence.
- Favicons read from the cache through T-260828-49's channel. A missing favicon
  falls back to the per-kind icon **with no layout shift** — the space is
  reserved before the image resolves, so a page does not reflow as icons arrive.
- Opening a link goes through the main process's external-open path, never a
  bare renderer navigation. `electron/main/security.ts` already guards navigation
  (T-260828-04); a link that navigates the renderer away from the app would defeat
  that.

**Out:** Links on person and engagement detail — the repository supports all
three, and those pages are T-260828-31 and a later engagement-detail task; this
scopes the company case, which is where the mockup draws them. Reordering links.
Link folders or grouping. Bulk paste of several URLs at once.

## Touches

- `electron/renderer/components/links/` — new
- `electron/renderer/views/CompanyDetail.tsx` — the section, after T-260828-29/30
- `electron/renderer/lib/query-keys.ts` — links keys and invalidation

## Acceptance

- [ ] Pasting a URL adds a row with the correct kind icon and no dialog
- [ ] A cached favicon renders; a missing one falls back to the per-kind icon and
      **the row's geometry is identical either way** — asserted, since this is
      the criterion most likely to be eyeballed
- [ ] With the network off, the section renders fully from cache and fallbacks
- [ ] Inline title editing saves on Enter and blur, and Escape reverts to the
      previous title without saving
- [ ] Clicking a link opens it externally; the renderer does not navigate
- [ ] A refused delete shows its reason, and the reason comes from the structured
      error rather than from parsing a message string
- [ ] Pasting something that is not a URL is refused visibly, not silently ignored
- [ ] Every action is reachable by keyboard, focus visible against the obsidian
      ground (X-06)

## Risks

- **Layout shift as favicons resolve.** A company with twelve links reflowing
  twice while icons arrive is the difference between the section feeling built
  and feeling assembled. Reserve the box.
- **Triggering a fetch per render.** The renderer asks for what is cached;
  T-260828-49's main process decides whether to fetch. A component that requests
  a fetch on mount turns opening a page into twelve outbound requests.
- **Navigating the renderer.** `security.ts` blocks navigation deliberately
  (T-260828-04). Links open externally through main, and a plain `<a href>` that
  happens to work in dev is the thing that breaks that guard in the packaged app.
- **The mockup is the authoritative visual spec** (AGENTS.md) — open it rather
  than inferring the row layout from this prose.

## Outcome

Merged. Built by a subagent under the build-only process; reviewed and verified
by the orchestrator at merge, with one accessibility finding closed on top.

**Changed:** `components/links/LinksCard.{tsx,css,test.tsx}` and `link-input.ts`
(all new), `views/CompanyDetail.{tsx,test.tsx}`, `lib/query-keys.ts`,
`lib/ipc.ts`, `lib/test-support/stub-crm.ts`, `shared/ipc-types.ts`,
`main/ipc/registry.ts`, `main/security.test.ts`.

### The dependency nobody had scoped

**The links IPC channels did not exist.** T-260828-48 built
`repositories/links.ts` and T-260828-55 hardened it, but nothing ever wired
either to the bridge: `CHANNEL_CONTRACTS` had no `links:*` entry, and no open or
closed task owned adding them — the builder grepped every scope file, and the
orchestrator confirmed it independently against `main`.

So this task was **unbuildable as scoped**, and the builder had to touch
`registry.ts` and `ipc-types.ts` — the two files its dispatch explicitly told it
to stay out of, because T-260828-40 owned them the same wave. It could not even
put the contracts in `ipc-types.ts` alone: `registry.ts`'s
`satisfies { [K in ChannelName]: … }` fails typecheck the moment a channel has no
handler.

**That is an orchestrator error, not a builder one** — file ownership for this
wave was derived by grepping each task file for the paths it mentions, which
finds what a task edits when its dependencies exist, and cannot find the file a
task needs *because something it depends on was never finished.*

The builder handled it about as well as it could be handled: it kept the
`registry.ts` edit to one import line and one contiguous block of four
`defineChannel` entries placed by the `favicons` section, reasoning that
T-260828-40's `db:stats` belongs near `db:schemaVersion` at the top — then said
so and asked for the merge order to be checked. **The two branches merged with no
conflict**, which is that placement discipline paying off rather than luck.

### Favicons render without reflow, as the channel was designed for

The row paints its `FAVICON_FALLBACK_ICONS` entry on first paint and swaps on a
later read. That works because T-260828-49's channel makes absence a *definite
answer* — `{ state: 'none', reason }`, never a pending promise — which is
precisely what the dispatch asked that task to guarantee for this one. Two tasks,
two waves apart, and the contract held.

### T-260828-53's two carry-overs, closed as instructed

Both were left open when T-53 could not touch `CompanyDetail.tsx`:

- **The `cadenceState` never-contacted guard.** The label reads "no contact
  logged" whether the bar is green or red, so the fix *is* the assertion — the
  test now asserts `DecayMeter`'s own `late` class rather than the text.
- **The `companiesById` three-query race.** The body now waits on
  `companies:list` as well as `companies:get`, with an error branch for it too.

Both verified by mutation: reverting the null branch to `{ pct: 0 }` fails the
first; dropping `companiesListQuery.isPending` from the render gate fails the
second.

### Two further files, both for correctness

`lib/ipc.ts` — the acceptance requires a refusal's reason to arrive as structured
data, and `unwrapMutationResult` was **dropping the envelope's `blocker` on the
floor**: `IpcCallError` had no field for it. Added as a readonly optional and
passed through. Purely additive; no existing call site changed.

`electron/main/security.ts` needed **no change at all.** The external-open path
this scope asks for already exists in `registerNavigationGuards` (T-260828-04):
a row's `<a target="_blank">` reaches `setWindowOpenHandler`, which denies the
window and calls `shell.openExternal`. The builder added a test pinning that
specific path for a link row rather than inventing a `shell:openExternal` channel
that would have duplicated the guard — the right instinct, since a second route
to the same capability is how a security guard gets bypassed later.

**Verified at merge:** typecheck clean across all three passes, lint clean, and
the whole suite green on the merged tree.

## Closed on top of the merge: the focus ring, again

The builder found `.quickadd input { outline: none }` in
`components/primitives/QuickAdd.css` — **the identical X-06 violation
T-260828-53 fixed in `sheets/fields.css`**, by the identical mechanism: a bare
`outline: none` beating base.css's global `:focus-visible` rule on equal
specificity and later source order.

Every QuickAdd in the app had no visible keyboard focus ring — the todos and
activity cards on this very page, the todos view, anywhere the primitive appears.
The builder avoided *inheriting* the bug by giving its paste field its own
`.linkadd` class, said so in a comment, and correctly left the primitive alone as
outside its scope.

Fixed here with the pattern T-260828-53 established:
`.quickadd input:focus:not(:focus-visible)`. A pointer click keeps the quiet
treatment the mockup wanted; a keyboard focus keeps the ring. Scoped rather than
deleted, for the same reason as last time.

That is the second instance of one defect ported verbatim from the mockup into a
second stylesheet. If a third appears, the right answer is a test over every
stylesheet in the renderer asserting no bare `outline: none` outside a
`:focus-visible` negation — a gate, not a third fix.

## One product judgement worth a later look

A URL like `example.com:8080/status` parses with protocol `example.com:` under
WHATWG rules. `normaliseLinkInput` treats a dotted scheme as a host and prefixes
`https://`, so that input works — flagged by the builder as a judgement call
rather than left implicit.

## What went wrong: a check reported clean that was not

**This branch did not typecheck.** `CompanyDetail.test.tsx` failed
`TS2349: This expression is not callable. Type 'never' has no call signatures.`
— and it failed **in the builder's own worktree**, not only after the merge. The
report said "npm run typecheck — clean, all three passes". It was not, so the
check was almost certainly run before the last edit to that file rather than
after it.

The defect itself is ordinary: `let releaseList: (() => void) | null = null`
assigned inside a `new Promise` executor. TypeScript's control-flow analysis does
not track that assignment, so at the release call the variable narrows back to
`null` and the optional call is `never`. Fixed by holding the resolver in an
object property, which is not narrowed that way — a real fix, not a suppression.

The thing to keep is the process point: **the orchestrator's gate is the only
reason this was caught**, and it was caught by re-running a check the builder had
already claimed to have run. A builder's report of its own checks is evidence,
not proof, and the merged-tree gate has now caught two failures in two
consecutive waves that a branch-level claim said were clean.
