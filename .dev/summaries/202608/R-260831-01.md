## What changed

Solo CRM ships a second Windows artifact. `npm run dist` now writes
`Solo CRM-Portable-<version>.exe` beside the installer — one file to copy onto a
USB stick, which keeps `solocrm.db` in the folder the `.exe` sits in and leaves
nothing in Program Files or the registry. The app works out that it is portable
by observing where it is running from, and refuses to start rather than put a
database anywhere it would be silently destroyed. The release overwrite guard,
which watched exactly one artifact, now watches every artifact the build
configures.

## Decisions

[ADR-013](../../decisions/ADR-013-portable-data-root.md). Three parts of it
matter without opening the file:

- **The portable marker is an observation, not a flag.** electron-builder's
  per-target options are `artifactName` and `publish` only
  (`app-builder-lib/out/core.d.ts:39`), and both Windows artifacts are packed
  from one build over one payload — so no define, marker file or `appId` can
  differ between them. The app instead concludes it is portable from
  `app.isPackaged` plus running out of a directory inside `os.tmpdir()`. This
  **removed a scoped deliverable from T-260831-04** and, with it, the class of
  bug where two halves of a marker drift apart and the portable build silently
  falls back to `userData`.
- **ADR-006's refusal of an environment variable is extended, not overturned.**
  ADR-013 states a four-part test an env var must pass to name a data location:
  build-written, a fact rather than a preference, corroborated by process state
  the environment cannot set, and unable to select anything the artifact's own
  placement does not already determine. A user-supplied `SOLOCRM_DATA_ROOT`
  stays refused.
- **The sync-folder guard is not relaxed for portable builds**, and
  `data-location.json` is ignored *and never written* in portable mode — a
  portable run writing that file would silently repoint an installed copy's data
  root on the same host.

## What went wrong

**The wave-1 builders were dispatched without worktree isolation and shared one
clone.** The orchestrator's fault: the `Agent` calls omitted
`isolation: "worktree"`, so both ran in the primary working directory against
one HEAD and one index. Three things followed.

1. Both ran `git checkout -B <task-id> main`, leaving HEAD on `T-260831-02`. The
   orchestrator's own "mark in-progress" commit then landed on that branch
   instead of `main` — which is why `45c84ff` sits in T-260831-02's history with
   nothing to do with that task.
2. T-260831-01's first commit landed on `T-260831-02` for the same reason. Its
   builder detected this, moved the commit, and reset `T-260831-02` back,
   verifying the reconstruction byte-identical.
3. T-260831-02's builder, finding another agent live in its working tree,
   committed through a temporary index with a compare-and-swap `update-ref`,
   never touching HEAD or the working tree.

Nothing was lost, and both builders reported the collision unprompted rather
than papering over it — the only reason this cost minutes instead of a re-run.
Each branch's content was verified against the working tree before merging
rather than taken on the reports. Waves 2 and 3 used `isolation: "worktree"`.
**The lesson is dispatch-shaped, not agent-shaped:** the preamble's
"unconditional reset" instruction assumes isolation, and without it that
instruction is what causes the collision.

**The machine's Node could not run the test suite.** System Node is v22.12.0
(Node-API 9); `better-sqlite3@13.0.3`'s prebuild needs Node-API 10 (Node >=
22.14.0) and *segfaults on the first `new Database()`* rather than failing to
load, which surfaces as ~21 `Worker exited unexpectedly` errors and 74/95 test
files passing — a symptom that looks like flaky infrastructure and is not. The
operator chose to keep the fix local to the run, so every command in the run was
prefixed with a PATH pointing at a Node 22.22.0 unpacked into a session
scratchpad. **That fix is temporary by construction and does not survive this
session**; the next run on this machine hits the same wall unless Node is
upgraded properly.

**A README sentence was false in a section that had just been rewritten.** It
claimed electron-builder writes `release/latest.yml` on every build.
T-260831-04's builder reported that neither of its builds wrote one, which
contradicted the `nsis`-only build run earlier the same day that did. Both
observations were true — adding the portable target changed the behaviour — and
the sentence was corrected at merge as a one-line fix. Recorded because the
builder flagged the contradiction instead of quietly editing around it, which is
what made it cheap to settle.

**Two scopes were wrong in ways review caught rather than the builders
absorbing silently.** T-260831-04 was scoped to produce a portable marker that
cannot exist, and T-260831-01's Scope item 1 originally asked the ADR to choose
an artifact shape the operator had already chosen. Both were corrected in the
task files before the affected builder read them. Scope written before the
constraints are known is the recurring cost in this process; the ADR-first
ordering is what surfaced it here rather than at merge.


**The portable QA could not be automated, and the attempt proved nothing.**
Driving the packaged app from this harness's shell session does not work: both
`Solo CRM-Portable-0.5.0.exe` and `release/win-unpacked/Solo CRM.exe` exit
almost immediately with code 0, write no database anywhere, emit no stdout or
stderr even under `ELECTRON_ENABLE_LOGGING=1`, and log no Windows error event.
Electron itself is fine here — the `runtime-boot-node` pool spawns real Electron
and passes — so it is specific to launching the packaged GUI app
non-interactively.

Worth recording because of how nearly it produced a false finding. Exit code 0
looked conclusive: the only `app.exit(0)` in `index.ts` is the
`firstRun.kind === 'quit'` branch, so the app appeared to be reaching the
first-run chooser — which would have meant the portable marker was not firing,
a release blocker. Planting a `solocrm.db` under the default root to suppress
the chooser entirely disproved it: nothing changed, and the planted file never
gained a `-wal` sidecar, so the app is not reaching `openDatabase()` at all and
the marker is neither confirmed nor impeached. The machine was left exactly as
found — no `%APPDATA%\Solo CRM`, no QA folders, no leftovers, no processes.

One deliberate restraint: the sync-folder step was not run against the real
`C:\Users\heavy\OneDrive`. The guard matches path segments, so a folder merely
named `OneDrive` exercises the identical code path without uploading a 121 MB
binary into the operator's cloud storage.
