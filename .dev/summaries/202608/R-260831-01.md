## Decisions

[ADR-013](../../decisions/ADR-013-portable-data-root.md) — a portable build
keeps its data beside the launched executable and learns where that is from the
launcher. Three parts of it are worth knowing without opening it:

- **The portable marker is an observation, not a flag.** electron-builder's
  per-target options are `artifactName` and `publish` only, and both Windows
  artifacts are packed from one build over one payload, so no define, marker
  file or `appId` can differ between them. The app instead concludes it is
  portable from `app.isPackaged` plus running out of a directory inside
  `os.tmpdir()`. This removed a scoped deliverable from T-260831-04 and the
  drift-between-two-halves bug that came with it.
- **ADR-006's refusal of an environment variable is extended, not overturned.**
  ADR-013 states a four-part test an env var must pass to name a data location
  — build-written, a fact rather than a preference, corroborated by process
  state the environment cannot set, and unable to select anything the
  artifact's placement does not already determine. A user-supplied
  `SOLOCRM_DATA_ROOT` stays refused.
- **The sync-folder guard is not relaxed for portable builds**, and
  `data-location.json` is ignored and never written in portable mode — a
  portable run writing that file would silently repoint an *installed* copy's
  data root on the same machine.

## What went wrong

**The wave-1 builders were dispatched without worktree isolation, and shared
one clone.** The orchestrator's fault: the `Agent` calls omitted
`isolation: "worktree"`, so both builders ran in the primary working directory
against one HEAD and one index. Three things followed.

1. Both ran `git checkout -B <task-id> main`, so HEAD ended up on
   `T-260831-02`. The orchestrator's own "mark in-progress" commit then landed
   on that branch instead of `main` — which is why `45c84ff` sits in
   T-260831-02's history with nothing to do with that task.
2. T-260831-01's first commit landed on `T-260831-02` for the same reason. Its
   builder detected this, moved the commit to `T-260831-01`, and reset
   `T-260831-02` back to `45c84ff`, verifying the reconstruction byte-identical.
3. T-260831-02's builder, finding another agent live in its working tree,
   committed through a temporary index with a compare-and-swap `update-ref`,
   never touching HEAD or the working tree.

Both builders recovered without losing work, and both reported the collision
unprompted rather than papering over it — which is the only reason this cost
minutes instead of a re-run. Nothing merged from a tree that was mid-collision:
the orchestrator verified each branch's content against the working tree before
merging. Waves 2 and 3 are dispatched with `isolation: "worktree"`.

**The machine's Node could not run the test suite.** System Node is v22.12.0
(Node-API 9); `better-sqlite3@13.0.3`'s prebuild needs Node-API 10 (Node >=
22.14.0) and segfaults on the first `new Database()` rather than failing to
load, which surfaces as ~21 `Worker exited unexpectedly` errors and 74/95 test
files passing. Not a code fault. The operator chose to keep the fix local to
the run, so every command is prefixed with a PATH pointing at a Node 22.22.0
unpacked into a session scratchpad. That fix is temporary by construction and
does not survive the session.
